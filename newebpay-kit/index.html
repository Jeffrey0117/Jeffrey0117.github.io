處理藍新的 padding

藍新的 AES 用 32 bytes 當單位補齊，不是標準 PKCS7 的 16。照標準寫，一部分真實通知會被拒收。

known-answer

一張訂閱怎麼走

以每月 299 元的方案為例，從使用者按下訂閱，到某天他退訂。

  1. 後端產生委託表單period() 把訂單、金額、週期加密成 PostData_，回傳表單網址和欄位。這一步不碰網路。
  2. 使用者在藍新輸入卡號前端把表單送出，卡號只經過藍新，你的伺服器碰不到。
  3. 藍新通知建立結果藍新打你的 NotifyURL，body 裡的 Period 交給 parsePeriodNotify() 解密，Status 是 SUCCESS 就開通。
  4. 之後每期自動扣款扣款排程在藍新那端，每期結果都會再打一次 NotifyURL。通知漏了藍新不會重送，所以要冪等，並用 queryPeriod() 對帳。
  5. 使用者要暫停或改方案alterPeriodStatus() 送 suspend 或 restart，alterPeriodAmt() 改金額或週期，交給 postForm() 送出。
  6. 使用者退訂送 terminate 結束委託。終止之後不能恢復，想保留回來的路就用 suspend。

接通知只要這幾行

金鑰放環境變數，驗章、解密、去 padding 都在套件裡。

const { createNewebpay } = require('newebpay-kit')

const pay = createNewebpay({
  merchantID: process.env.NEWEBPAY_MERCHANT_ID,
  hashKey: process.env.NEWEBPAY_HASH_KEY, // 32 字元
  hashIV: process.env.NEWEBPAY_HASH_IV,   // 16 字元
  sandbox: process.env.NEWEBPAY_SANDBOX === '1',
})

// 單次付款的 NotifyURL：驗章不過直接 throw
const result = pay.parseMpgNotify(req.body)
// { Status: 'SUCCESS', Result: {…} }

// 定期定額每期的 NotifyURL
const notify = pay.parsePeriodNotify(req.body.Period)
if (notify.Status === 'SUCCESS') extendMembership()

建立時會先檢查金鑰長度：hashKey 不是 32 字元、hashIV 不是 16 字元就直接報錯，不會等到第一筆交易才發現。

1.0.0 修掉一個實際踩到的問題：舊版解密只接受 1 到 16 的 padding，但藍新官方以 32 bytes 為單位補齊，真實通知的 pad 值可能到 32，於是合法通知被整批拒收。現在接受 1 到 32，並逐個 byte 檢查，金鑰錯了仍然會拒收。

sandbox: true 會改打測試站，要搭配藍新測試平台另開的測試商店金鑰，正式金鑰在測試站一定失敗。
